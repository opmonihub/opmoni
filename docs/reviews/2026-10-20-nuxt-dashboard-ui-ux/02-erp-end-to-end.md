# Opmoni ERP end-to-end UI/UX audit

Audit scope: ERP routes, shared shell and company context, operating behavior, states, and source-level comparison with the actual local Nuxt UI dashboard template. The ERP source checkout was pinned by the task brief to `810506f518651f268ec67a8b451c2f832388b0bf`. The source tree was not modified. No service, browser, build, test, install, or data operation was run for this audit; separately recorded Task 11 coordinator browser acceptance on this exact source is cited below.

## Executive assessment

The ERP is an authentic Nuxt UI dashboard application, not a visual copy of the demo. The shared shell follows the template's `UDashboardGroup` / collapsible-resizable `UDashboardSidebar` / `UNavigationMenu` / `UserMenu` pattern and adds the selected Company and delegated Account context. Catalogs, finance, reports, company administration, contract, and commercial setup pages contain meaningful API-backed flows. Several other top-level routes are deliberately honest read-only hubs, but their OpenSpec requirements describe full operating workflows. Those routes remain incomplete even though API paths and action buttons exist in the module contract.

The highest-confidence user-impact findings are:

1. **P2 — A narrow cross-tab refresh race can leave Company settings stale.** The ordinary in-tab Company switch clears non-access Nuxt state and does a full navigation, and the focus plugin reloads when it observes an account/company change. The gap is narrower: a finance 409 can refresh `/me` and commit the newly selected Company before the old tab's focus handler compares identity; that handler then sees the new Company as both its “previous” and current value. Since `erp-company-settings` has fixed global state keys and the settings form skips GET when state is non-null, a later settings visit in that tab can reuse the old Company's values. A save could submit them to the new Company. See `useAuth.ts:13-17,35-53,80-90`, `access-focus.client.ts:8-25`, finance denial handling `useErpFinanceWorkspace.ts:194-260`, and settings state/form `useErpCompanySettings.ts:5-15`, `ErpSettingsSectionForm.vue:20-34`.
2. **P1 — Cash has no operating flow at the frozen source.** `/erp/caixa` is a generic paginated read-only hub. It has no register creation, session opening, movement, payment, reconciliation, or close UI. The new cash workflow test is untracked and not implemented at this source freeze, consistent with the Task 12 hold. See `frontend/app/pages/erp/caixa/index.vue:7-9`, `frontend/app/components/erp/ErpModuleHub.vue:73-126,181-208`, and canonical `openspec/specs/erp-finance-and-cash/spec.md:31-49`.
3. **P1 — Purchases, stock, sales, fiscal issuance, and accounting delivery are not complete operating workspaces.** Five routes expose generic collection previews; the purchases route adds XML preview only. There are no dedicated create/edit/post/return/adjust/transfer/issue/retry/detail workflows in those route components. OpenSpec requires these user flows. See route mappings in `frontend/app/utils/erpModulesNav.ts:138-293` and canonical specs listed in the coverage appendix.
4. **P2 — Generic Company settings lack recovery and server field feedback.** `ErpSettingsSectionForm` displays a toast on save failure, but does not map 422 field errors or provide a retry control; its initial refresh is not rendered as an explicit retryable error state. This is less robust than the operational catalog, finance, and report flows.
5. **P2 — Generic operating hubs expose raw API rows as a table.** Users see up to six backend property names and values, without business formatting, status vocabulary, detail or row actions. These screens are useful as a safe “API still unavailable / consultation only” boundary, but cannot substitute for the workflows promised by their descriptions.

There is no evidence in this source audit for a P0 issue. Task 11's separate coordinator report provides bounded browser acceptance on this exact source for desktop finance mutations, a private receipt, and mobile layout/context isolation. It does not cover finance date/aging behavior, full ERP browser acceptance, current built-bundle contrast, or the requested current browser-side template comparison; those remain outside this report's evidence.

## Shared shell, context, permissions and navigation

The ERP shell adopts the actual template dashboard frame: `UDashboardGroup`, collapsible/resizable left `UDashboardSidebar`, vertical `UNavigationMenu`, sidebar footer user menu, and `UDashboardPanel` headers (`frontend/app/layouts/erp.vue:33-90`). This directly matches `.dashboard/app/layouts/default.vue:117-161`. Company name replaces the demo team selector in the sidebar. In the collapsed state there is a company icon/button; the expanded header mounts `WorkspaceContextMenu` (`erp.vue:43-53`). Mobile headers expose `CompanyMenu` and `UserMenu` (`erp.vue:71-89`). Navigation items are filtered by current Company permission grants, and every selected item closes the mobile sidebar (`erp.vue:14-24`; `app/utils/erpModulesNav.ts:63-75,337-359`).

The shell keys protected route content by Account, Company and access kind (`erp.vue:8,70,87`), and custom sidebar navigation restores focus after route changes (`app/composables/useErpSidebarNavigation.ts:4-30`). Those are justified tenant/context adaptations; the demo has no Company/office boundary and no comparable authority model. Page-level composables add actor, Company, office, session-generation and action checks before API operations. Company switching must not be reduced to a visual team selector: the canonical foundation requires `X-Company-Id`, explicit delegated-office binding, stale-state clearing and server authorization (`openspec/specs/erp-company-foundation/spec.md:20-63`).

The ERP intentionally leaves out the demo's global search and notification sample slideover. The demo's global search points to template source (`.dashboard/app/layouts/default.vue:75-89`); its notifications and sample endpoints are not ERP business capabilities. Omitting them is a correct product adaptation. ERP navigation also uses explicit domain names and read-grant filtering instead of exposing every demo nav destination.

One caveat is inconsistent authorization presentation: catalogs, finance, labels, reporting and company administration generally gate the exact actions in the UI; generic settings show Save controls and rely on the backend to reject disallowed writes. Backend authority remains primary, but disabled/hidden controls and inline permission messaging would make the current role/access state legible.

## Cross-module patterns

### Positive patterns to preserve

- Shared ERP layout and native Nuxt UI primitives keep the application recognizable while providing Company context and access-aware navigation.
- Catalog forms consistently use a business record label, named fields, reference selectors, lossless decimal/codes, view-only detail mode, confirmation before archive, and restoration of keyboard focus after row actions.
- Company and office context is captured and checked across catalog/finance/report operations; stale responses from a prior context are discarded. The native Company switch itself clears non-access Nuxt state and redirects to the Company overview; Task 11's exact-HEAD browser report also verified Company A→B clearing during the mobile finance flow. The separate P2 finding concerns a source-derived cross-tab finance-refresh ordering path, not the ordinary switch.
- Financial writes are explicit and recoverable. Finance keeps decimal amounts as strings, accepts server-authored totals and statuses, blocks repeated uncertain writes, and does not treat a timeout as permission to post twice.
- Notes/files distinguish private from shared content and enforce author-specific privacy actions; the historical Task 25 browser report tested that owner, manager and viewer views do not collapse those boundaries.
- Reports label applied filters, use server snapshots, distinguish fiscal outcomes, and verify export state and expiration before download.
- Explicit placeholder copy is preferable to fabricated balances, fictional sales activity or disabled controls that imply a working transaction.

### Systemic gaps and risks

- Several domain routes use one dynamic “first six object keys” table. It is not a substitute for a typed table, domain status copy, detail route, row actions or mutation workflow.
- The module contract has read and write grants, but generic hub interactions only use `readPermission`; `writePermission` is declarative and no write operation consumes it (`frontend/app/utils/erpModulesNav.ts:51-60`; `ErpModuleHub.vue:16-18`). Button presence/API tab presence alone must not be counted as write acceptance.
- Generic settings centralize fields and API transport, but do not yet have scoped Company cache identity, action-level UI gating, field-level 422 handling, or structured retry/error presentation.
- `/erp/configuracoes/sms` and `/rotulos` are explicitly unfinished placeholders. `/erp/configuracoes/prefixos` only edits a SKU prefix while its own copy says the JSON prefix editor is future work.
- Route existence is much broader than current operating-workflow coverage. The canonical specs remain the completion authority; this audit does not change their status.

## P1 / P2 findings

### [P2] A cross-tab finance refresh can leave Company settings stale

- **Location:** `frontend/app/composables/useErpCompanySettings.ts:5-7,9-15`; `frontend/app/components/erp/ErpSettingsSectionForm.vue:20-34,37-46`.
- **Category:** Tenant isolation / state integrity.
- **Impact:** The standard `switchCompany()` path is protected: it updates identity, calls `clearAccountData()` (which clears non-access Nuxt state), rotates CSRF, then uses `window.location.assign('/erp')` (`frontend/app/composables/useAuth.ts:80-90`). The client focus plugin also compares the pre-refresh and post-refresh Company and reloads to the access destination when they differ (`frontend/app/plugins/access-focus.client.ts:8-25`).
- **Concrete gap path:** Keep Company A settings loaded in one tab, then visit Finance in that tab while an old Company A finance read is in flight. In another tab, switch the shared server session to Company B. If the old finance request resolves with 409 and its denial handler commits Company B identity before the first tab's focus handler captures identity, `refreshWithStatus()` updates `user` but does not call `clearAccountData()` or reload (`frontend/app/composables/useAuth.ts:35-53`; `frontend/app/composables/useErpFinanceWorkspace.ts:209-260`). The focus handler then records B as `previousCompany`, refreshes B, sees no difference, and does not reload (`access-focus.client.ts:12-25`). The ERP layout remounts route content on Company key changes (`frontend/app/layouts/erp.vue:8,70,87`), but the fixed `erp-company-settings` Nuxt state survives (`useErpCompanySettings.ts:5-7`); when the user later opens settings, the form skips its read because that state is non-null (`ErpSettingsSectionForm.vue:20-34`). The next save uses current Company context and patches the currently displayed subset (`ErpSettingsSectionForm.vue:37-46`).
- **Confidence and severity:** Source-backed race path, not a claim that ordinary Company switching leaks state. Probability is narrower than a normal in-tab switch, so P2; a stale save could still overwrite selected settings in B. No browser reproduction was run.
- **Recommendation:** Scope settings state to actor/Account/Company/access kind or make it component-local; also clear it synchronously whenever auth refresh changes Company and fence late reads/writes. Require a current-context settings read before enabling Save. Add a focused regression for the 409-refresh-before-focus ordering and a separate check that the normal native switch still clears state.
- **Standard:** Company/session-scoped data isolation; `openspec/specs/erp-company-foundation/spec.md:42-63` requires clearing stale protected UI state on successful switch and context-bound SSR/late responses.

### [P1] Cash route does not support the cashier workflow

- **Location:** `frontend/app/pages/erp/caixa/index.vue:1-9`; `frontend/app/components/erp/ErpModuleHub.vue:73-126,181-208`.
- **Category:** Functional completeness / finance safety.
- **Impact:** A cashier can at most read a generic register/session row. There is no opening amount, movement entry, explicit cash-payment session selection, declared count, discrepancy confirmation, close, or reconciliation path. The user cannot complete the cash task from the ERP UI.
- **Evidence:** The route renders only `ErpModuleHub`. The Task 12 checkpoint lists the unsupported flows and safety conditions. ### [P1] Core purchase, inventory, sales, fiscal and accounting flows remain hub-only

### [P2] Generic module tables expose backend keys, not business records

- **Category:** Usability / information design.
- **Impact:** Column titles are derived from object keys and values are rendered without domain formatting; row status, currency, fiscal state, relation names, and actions remain unmodelled. Users must interpret backend-shaped data and may mistake low-level rows for completed workflows.

### [P2] Generic Company settings have weak error recovery and UI permission feedback

- **Location:** `frontend/app/components/erp/ErpSettingsSectionForm.vue:20-47,83-133`; tabs `frontend/app/pages/erp/configuracoes.vue:15-38`.
- **Category:** Error handling / authorization UX.
- **Impact:** Initial read failure is not rendered as a dedicated retry alert; save failures collapse to a toast and lose 422 field-level feedback. Every generic settings page renders Save regardless of the current Company action grants; the server still decides, but viewers/delegated readers receive little pre-submit explanation.
- **Evidence:** `onMounted` awaits `refresh()` without a catch path or local load-error state (`:20-24`); `onSubmit` catches all failures and emits one generic toast (`:37-46`); fields have no API error binding (`:103-130`). Settings navigation conditionally hides only specific owner/establishment tabs, not generic write tabs (`configuracoes.vue:15-38`).
- **Recommendation:** Add per-field `apiFailure`/422 mapping and inline retryable read error; gate Save by the exact action/current Company permission and show a localized read-only explanation. Retain edits on a transient failure.

### [P2] Purchase XML preview cannot recover the selected file, rejects its advertised upper size, and cannot reach posting

- **Location:** `frontend/app/components/erp/ErpPurchaseXmlPreview.vue:19-41,45-94`; parser `backend/app/Erp/Stock/ErpPurchaseXmlPreviewService.php:54-57`; Nuxt ingress cap `frontend/server/api/v1/[...path].ts:14-41`.
- **Category:** Error recovery / workflow completeness.
- **Impact:** A read/preview error leaves only an alert; the native file input is reset in `finally`, so the user must reselect the XML. The UI accepts files up to 5 MiB, while the backend parser rejects XML above 2,000,000 bytes; the Nuxt proxy also caps the complete request body at 4 MiB. Thus some files allowed by the picker cannot be previewed, and near-limit payloads may hit the proxy cap once JSON overhead is included. A successful preview has no confirmation action and explicitly stops before a purchase is posted.
- **Evidence:** The component checks `file.size > 5 * 1024 * 1024` and then posts the file text as JSON; `input.value = ''` runs for every outcome and there is no retry or confirm function (`ErpPurchaseXmlPreview.vue:27-40`). The backend parser enforces `strlen($xml) > 2_000_000` (`ErpPurchaseXmlPreviewService.php:54-57`); the Nuxt proxy enforces a 4 MiB total request-body cap (`frontend/server/api/v1/[...path].ts:14-41`).
- **Recommendation:** Preserve selected file/draft on recoverable errors and offer retry; add the canonical idempotent explicit confirmation flow only when the purchasing implementation is approved.
