# ERP forms: independent contract and reference audit

Method: source-based independent specialist review in the isolated snapshot; no application mutation, test execution, dependency installation, browser, or further delegation. Browser measurements below are coordinator-provided evidence, not this worker's execution. The coordinator reviewed the report and distinguished existing defects from the newly requested tax-profile capability.

## Decision summary

Basic product creation already accepts incomplete fiscal data. The principal defect is that its presentation makes every fiscal field and variant look like part of the initial task. Preserve this permissive save contract and provide a short basic editor plus optional advanced sections. Reusable tax configurations are a separate supported product requirement to specify: existing company defaults are stored but are not resolved into product creation or a product tax-profile relationship. Hiding fields alone does not implement that requirement.

No product-dialog transparency defect is confirmed. Coordinator measured the settled product-create dialog at opacity 1 with rgb(255,255,255), no filter/backdrop, and did not reproduce transparency. At 1280x800 it measured a 768px drawer, 654px visible body, 1650px scroll height, 32 labels, and the create action at y=1651 outside the initial viewport. At 390x844 mobile it measured 698px visible body, 2766px scroll height, 32 labels, and submit at y=2799, with no horizontal overflow and the same opaque white surface. No submission occurred. Source independently confirms the long layout and action placement.

Authority: `.dashboard` controls presentation; `openspec/specs/` controls product behavior. Legacy references provide workflow evidence, not permission to replace company tenancy or immutable commercial/fiscal contracts. The dated acceptance report is evidence of its listed scenarios, not proof of usability completeness: `docs/architecture/erp-local-acceptance-2026-10-23.md:21-33` explicitly lists scoped corrections and native flows.

## Prioritized findings

### F1 — P2: A basic product task is visually submerged in an issuance-size editor

- **Evidence:** `frontend/app/components/erp/catalogs/ErpProductCatalogForm.vue:330-528` always renders all fiscal groups, followed by variants `:530-638`, then Save `:641-647`. `frontend/app/components/erp/catalogs/ErpCatalogResource.vue:428-435` uses the same 3xl drawer for every resource; `:492-500` keeps only Fechar in its footer. Coordinator browser measurements above confirm the primary action starts outside view.
- **Contract/pattern:** API minimal requirements are only name/unit (`backend/app/Erp/ErpCatalogWriteService.php:182-185`); fiscal fields nullable `:273-288`; `.dashboard/app/components/customers/AddModal.vue:30-54` groups short task and actions; `openspec/specs/erp-company-foundation/spec.md:61-80` requires reachable actions and established dashboard presentation.
- **Legacy:** both `reference/sistema/resources/views/product/create.blade.php:415-519` and `reference/sistema-e7b77be/resources/views/product/create.blade.php:415-519` prefill business tax defaults; both edit `:433-532` use saved product values. Existing current empty fiscal fields are intentionally permitted, not a missing required validation.
- **Impact:** user perceives tax work as prerequisite to a basic product; the only primary action competes poorly with persistent close.
- **Minimum refactor:** short basic identity/unit/price section; optional Fiscal, Commercial details and Variants progression using Nuxt UI patterns. Put primary Save/Cancel in a reachable shared form action area, with native form association. Decide drawer versus full-page editor by complexity; no transparency patch without reproduction.
- **Regression:** basic create with only name + native unit; no fiscal values; edit nulls and existing tax values; adding/archiving multiple variants; narrow keyboard/focus; footer submission and pending state; exactly one dialog; close/backdrop/Escape must not accidentally discard dirty edits without explicit policy.

### F2 — P2, requirement gap: Company tax defaults and the product editor have no effective inheritance contract

- **Evidence:** defaults are editable in `frontend/app/pages/erp/configuracoes/sistema.vue:12-21` and persistable in `backend/app/Erp/ErpCompanyOperatingSettings.php:23-24`. Product initialization reads only record-or-empty (`frontend/app/components/erp/catalogs/ErpProductCatalogForm.vue:77-91`); create validation/save applies no company tax-default resolver (`backend/app/Erp/ErpCatalogWriteService.php:68-89`, `:178-233`). No tax-profile relationship exists in `backend/app/Models/Erp/ErpProduct.php:17-24` or `frontend/shared/types/erpCatalogs.ts:27-58`. `ErpTaxRateCatalogForm.vue:14-26` edits one named rate/kind, not a full multi-tax product configuration.
- **Legacy:** both `reference/sistema/resources/views/product/create.blade.php:418-475` and `reference/sistema-e7b77be/resources/views/product/create.blade.php:418-475` initialize from business defaults; both edit `:433-488` initialize from product fields. This is create-time prefill plus stored override, not evidence of a dynamic linked reusable tax profile.
- **Contract:** `openspec/specs/erp-core-catalogs/spec.md:20-32` and `openspec/specs/erp-sales/spec.md:38-40` freeze historical meaning. `frontend/shared/utils/erpFiscal.ts:72-99` consumes frozen product fields; `backend/app/Erp/Fiscal/ErpFiscalIssuanceService.php:520-528` rejects different NCM/classifications. A tax-empty product can be saved; a tax-empty posted snapshot cannot simply be repaired by editing today's catalog.
- **Impact:** advertised company defaults do not reduce repetitive per-product tax entry. A simplistic later fallback to current defaults would rewrite the meaning of old transactions and hide missing fiscal prerequisites.
- **Minimum plan extension:** specify a reusable, company-scoped tax configuration covering ICMS/PIS/COFINS and optional IPI/IBS-CBS, applicable regime/context, explicit product overrides, and visible effective-value provenance. Proposed precedence for design review: explicit product override > selected reusable tax configuration > explicitly applicable company/establishment default > unresolved. Decide whether inheritance is dynamic until operation snapshot, how null differs from inherit/clear/zero, effective revisions and what happens when a profile changes. Keep product creation permissive. Resolve and freeze before the applicable commercial/fiscal snapshot; issuance validates complete model facts and must not weaken builders. This is a new domain/API change, not a visual-only refactor or a provisioning task.
- **Regression:** two products sharing a configuration; one overriding only PIS; explicit zero rate versus null/inherit; regime changes; profile update affects future drafts only; posted sale fiscal preparation still uses frozen values; tax-empty basic create succeeds; issuance missing required classification fails before dispatch; tenant isolation; inactive/deleted profile retains history; no same-number legacy/native assumptions.

Do not change product fiscal fields to universally required or silently discard a saved code absent from a current list.
- **Regression:** `00`, `01`, `101` round trip unchanged; archived/unknown current values; keyboard search; empty fiscal profile; regime-dependent optionality; selectors serialize current destination names and types.
