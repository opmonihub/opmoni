# ERP forms, initial setup and reusable product tax configurations

Status: planned, not implemented. This extends the [visual alignment plan](visual-alignment-plan.md) with V07–V09. The user explicitly requested **settings and basic catalogs**, and a product flow that can save a basic record without entering every tax field, using reusable tax configurations for ICMS, PIS, COFINS and related fields. No settings, records, application code or release gates were changed during this audit.

## V09 — Reuse product tax configurations with explicit inheritance

This is a new domain/API capability requested by the user. Define it in an in-flight OpenSpec change before implementation, covering core catalogs, company setup, Sales and fiscal source preparation. The base `.dashboard` remains the visual authority; native snapshots and fiscal builders remain the behavioral authority.

### Proposed minimal contract

Use a company-scoped named tax profile with active/inactive state and a revision, containing supported ICMS, PIS, COFINS, optional IPI/Simples credit and existing IBS/CBS classification fields. A profile reduces repeated setup; it does not certify a tax treatment or replace operation-specific calculation. Keep NCM/CEST and product identity explicit; any suggested classification must be visible and reviewable rather than universally assigned to all products.

Proposed field resolution is **explicit product override → selected applicable profile → explicitly configured compatible company default → unresolved**. Company defaults may select a profile. An establishment-specific default may participate only if its native scope and precedence are explicitly defined; none is assumed to exist today. Validate compatibility against the actual regime/establishment/operation context. Use the current operation-nature/CFOP catalog for operational facts instead of inventing a duplicate universal product CFOP.

That precedence applies to fields intentionally set to inherit. A profile explicitly selected by the user but archived, unavailable or incompatible is a visible resolution error, not permission to silently substitute the company default. Distinguish “no profile selected/use company default” from an invalid existing selection, including after lookup failure or permission changes.

Keep the first version limited to explicit profile selection/defaults and supported conditions. Do not introduce an unrestricted dynamic rules language. Future condition sets require a defined context, deterministic precedence, conflict behavior and tests; a company/product setting alone cannot establish every destination- or operation-dependent tax result.

| User intent | Proposed semantic contract |
| --- | --- |
| Use the configuration | Explicit inherit state; resolve a profile/default when applicable. |
| Change only PIS for one product | Product-specific override for that field; other fields keep their source. |
| Explicit zero rate | Valid exact decimal zero; do not treat it as missing or use truthiness fallback. |
| Leave a tax fact unresolved | Explicit no-value state if permitted by the catalog; it must not silently fall through to another default. Issuance still rejects a missing required fact. |
| Edit existing product | Preserve current explicit field values. Do not infer that an old null meant “inherit”; expose a deliberate adoption action for the new behavior. |
| Profile changes | New operations may use the new revision; saved draft updates require an explicit refresh/review policy. Posted operations keep frozen values and provenance. |

The existing API uses omitted keys for “unchanged” and explicit fiscal null for “clear”. Preserve that contract; introduce inheritance intent explicitly rather than overloading null. The implementation may retain current product fields as override storage and add focused relationship/intent metadata. Avoid converting every existing product into a linked profile or copying profile values into all product rows on each edit.

- [ ] Define schema/API/permissions for profile CRUD, scoped references, company default selection, per-product field intent, revisions and archive/history. Reuse existing company write fencing/audit and catalog contracts. Keep fiscal codes as strings and rates as exact decimals.
- [ ] Build one authoritative server resolver returning effective values, source and profile revision, plus unresolved/incompatible facts. Use the same result in product preview and operational preparation; the client preview is never the authority for totals or issued facts. Resolve and persist one coherent profile/default revision under concurrent edits, using the existing transaction/locking or optimistic-revision conventions.
- [ ] Add product UI with a short “Configuração tributária” selector, effective-value summary and “Personalizar” action. Show the source and exceptions when expanded. Preserve basic saving without any profile; never imply that catalog completeness guarantees fiscal authorization.
- [ ] Integrate resolution into `ErpCommercialDraftService` and the relevant source builders before their snapshots freeze. Store effective tax facts and profile/revision provenance. Coordinate any changed snapshot shape/version with existing consumers. Profile selection must not double-apply the standalone `ErpTaxRate`, alter totals implicitly or bypass price/discount authority.
- [ ] Define an explicit commercial operation intent/selected fiscal model, rather than infer fiscal intent from the existence of a product profile. Add model-specific fiscal-readiness feedback before that fiscal-intended operation becomes immutable. Surface missing facts with actions to resolve/review and rebuild the eligible draft; keep non-fiscal/basic catalog use available. Preserve the existing posted-source equality checks. Historical tax-empty sales need an explicit supported correction workflow, not a fallback to today's profile.
- [ ] Define draft refresh behavior: a profile change cannot silently replace a reviewed draft's taxes/prices; show the change and require a fresh calculation/review where applicable. Profile archive/deletion preserves historical references and blocks invalid new use.

Acceptance scenarios: two products share one profile; one overrides only PIS; zero remains zero; `01` remains a string; unrelated fields inherit visibly; incompatible/archived/unavailable selected profiles fail without fallback; a profile revision affects only newly resolved/reviewed operations; existing products, including historical null fields, do not change without adoption; concurrent profile changes cannot produce a mixed-revision operation; posted Sales/fiscal/financial snapshots remain identical. Missing required fiscal facts fail before dispatch. Basic products and operations without declared fiscal intent do not acquire universal fiscal requirements. All relationships are company-scoped and honor delegated grants and establishment restrictions.
