# Independent layout and component audit

Scope: current-source snapshot `layout/`, comparing `frontend/app/` directly with `.dashboard/app/`. Read-only review; no product edits, browser sessions, detector output, dependency installation, or test execution. The snapshot includes app sources and package metadata but does not include `frontend/tests/`; regression checks below describe behaviors to preserve, not tests claimed to pass. Nuxt UI dependency declared in `frontend/package.json` is `^4.11.3`.

The template is a reference for presentation and composition, not a product specification. ERP issuance, permissions, establishments, reconciliation, XML imports, office capture, and accounting delegation are legitimate product functionality. None should be removed because the demonstration template lacks them. No P1 issue was established in this source-only review. P2 means a concrete usability/consistency problem worth addressing in the next refactor; P3 means a smaller presentation inconsistency. Browser-dependent consequences are explicitly identified as inferences.

## L1 — P2: Fiscal processing does not participate in its parent's scroll contract

- **Current evidence:** `frontend/app/pages/fiscal.vue:22` makes the dashboard body a constrained flex area with `overflow-hidden`; its body renders only `NuxtPage` at line 38. `frontend/app/pages/fiscal/processamento.vue:123` supplies a plain `space-y-4 p-4` root, then a potentially long list at line 178 and pagination at line 199. There is no `overflow-y-auto`, `flex-1`, or `min-h-0` scroll owner in this child.
- **Template comparison:** `.dashboard/app/pages/customers.vue:223` keeps the list inside the ordinary dashboard body, without disabling its scroll behavior. Its pagination remains part of that body at line 313. `.dashboard/app/pages/inbox.vue:51` deliberately gives separate operational panes their own dashboard panel structure instead of relying on content escaping an overflow-hidden parent.
- **Expected pattern / UX impact:** a long processing list needs an explicit scroll owner. The sibling `frontend/app/pages/fiscal/index.vue:238` already uses `pageScrollClass`; `frontend/app/utils/pageShell.ts:18` defines the matching flex and overflow contract. Source suggests long processing pages can put lower rows and pagination outside the reachable panel area. This is an inference requiring a populated browser check, not a reproduced clipping claim.
- **Shared root / affected pages:** Fiscal shell and `/fiscal/processamento`; the other Fiscal children already select explicit body classes and should be preserved.
- **Minimal refactor:** reuse `pageScrollClass` on this child, retaining its operational content and keeping pagination in that scroll root. Avoid a global change to `fiscal.vue`, because document/client tables intentionally own different scroll behavior.
- **Preserve / regression checks:** initial loading versus previously confirmed summary, stale-data warning, state filter, pagination, authorization/attempt/deadline fields, fiscal explanatory information, account changes. Check a full 15-row page on a short desktop viewport and mobile; ensure the final row and pagination remain reachable without introducing two page scrollbars.

## L2 — P2: Company settings is one 35-row form with no task-based grouping

- **Current evidence:** `frontend/app/utils/erpCompanySettingsFields.ts:14` defines 35 business fields. Identification is immediately followed by profit/decimal/currency preferences at lines 20–23, calendar/accounting settings at lines 24–29, address/contact at lines 30–35, and fiscal numbering/series/credentials at lines 36–49. `frontend/app/components/erp/ErpSettingsSectionForm.vue:148` renders all entries into one subtle card with only repeated separators. `frontend/app/pages/erp/configuracoes/empresa.vue:8` passes this complete array into a single section.
- **Template comparison:** `.dashboard/app/pages/settings/index.vue:57` defines a compact, named task header and `.dashboard/app/pages/settings/index.vue:73` contains the fields for that one task. `.dashboard/app/pages/settings/security.vue:27` and line 60 split Password and Account into separate task cards. The template's literal five-field count is not the rule; coherent tasks are.
- **Expected pattern / UX impact:** an operator changing an address should be able to locate address fields without scanning document numbering, financial preferences, and legacy identifiers. Repeated row styling alone does not explain this domain hierarchy. The larger `max-w-4xl` in `frontend/app/pages/erp/configuracoes.vue:28` is reasonable for the product; the missing grouping is the problem.
- **Shared root / affected pages:** `ErpSettingsSectionForm` plus its field definitions; directly `/erp/configuracoes/empresa`, with a reusable grouping approach available to other long settings sections.
- **Minimal refactor:** add optional named field groups to the existing component and divide this page into Identification, Address/contact, Preferences, and Fiscal parameters. Keep one existing form state and save operation initially; headings/cards or explicit sections suffice, without a wizard, new routes, or new dependencies. Separate raw ID replacement into a domain/API task rather than hiding required values during a styling refactor.
- **Preserve / regression checks:** all existing field keys and value types, metadata options, 0/1 checkbox serialization, API field errors, one PATCH payload for the current section, authorization invalidation, pending/disabled behavior, failed-load recovery, fiscal environments and numbering values. Avoid introducing per-card saves that could silently change patch semantics.

## L3 — P2: ERP membership and establishment administration rebuild form primitives and overwhelm list context

- **Current evidence:** `frontend/app/components/erp/ErpCompanyAdministration.vue:426` expands the editor directly before the search/list. Name/CNPJ/status use hand-styled native inputs/select at lines 443–472; identity and role repeat that pattern at lines 478–519; permissions and establishment scope use raw radio/checkbox controls at lines 530–568. The same component displays every effective permission as a badge at lines 698–706, which can turn one member into a large block. These are not missing features: they are independent implementations of presentation already handled elsewhere.
- **Template comparison:** `.dashboard/app/components/customers/AddModal.vue:26` uses an action-triggered overlay, with `UForm` / `UFormField` / `UInput` at lines 30–40. `.dashboard/app/components/settings/MembersList.vue:20` uses compact, aligned member rows; role and row actions use `USelect` and `UDropdownMenu` at lines 43–55.
- **Expected pattern / UX impact:** opening a permission editor should not push the member list far down the page, and role/identity controls should have the same sizing and states as other Opmoni settings. Permission membership is important, but an always-expanded wall of technical permission names reduces the visibility of identity, role, and establishment scope.
- **Shared root / affected pages:** one shared `ErpCompanyAdministration`, used by `frontend/app/pages/erp/configuracoes/membros.vue:6` and `frontend/app/pages/erp/configuracoes/estabelecimentos.vue:6`.
- **Minimal refactor:** preserve the administration composable/state and replace the visual controls with the existing Nuxt UI field/input/select/checkbox/radio components. Put create/edit inside the established slideover/modal pattern; the catalog editor at `frontend/app/components/erp/catalogs/ErpCatalogResource.vue:428` already provides a local reference. Summarize grants by role/count in rows and expose the complete list on detail or an explicit expansion. Keep a compact list, rather than forcing every member into a customer-style table.
- **Preserve / regression checks:** identity lookup must remain limited to existing identities; direct owner restrictions, protected owner removal/demotion, default/custom permission semantics, all/selected establishment scope, selected establishments across pages, two distinct pagination cursors, stale-data blocking, authority changes during in-flight requests, disabled mutations and exact field-error associations. Moving into an overlay needs keyboard close and focus-return verification; this audit does not claim an existing accessibility failure.

## L4 — P2: Fiscal document browsing permanently includes the full creation form

- **Current evidence:** `frontend/app/components/erp/ErpFiscalWorkspace.vue:338` creates a left list/right detail grid. Inside the left list column, line 361 renders the entire “Novo rascunho fiscal” card whenever create permission and configuration exist; it is not conditional on an explicit creation action. The document list is separately capped at `max-h-[34rem]` with its own scrolling at line 345. On smaller screens the detail section at line 398 comes after this create card. The form itself introduces fiscal model/type at `frontend/app/components/erp/ErpFiscalDocumentForm.vue:238`, then potentially many recipient, per-item tax, totals, and payment fields at lines 363–434.
- **Template comparison:** `.dashboard/app/pages/customers.vue:217` keeps creation in a navbar action; `.dashboard/app/components/customers/AddModal.vue:26` only presents the editor after activation. For a list/detail tool, `.dashboard/app/pages/inbox.vue:75` renders the list then the selected detail, with mobile detail in a slideover at line 84.
- **Expected pattern / UX impact:** review and creation are separate tasks. Browsing a fiscal document should not require scrolling past a creation workflow, especially on a single-column viewport; the default expanded form competes with selected document actions and introduces a second scroll area. The necessary fiscal data and safety gates are not the drift—the always-expanded placement is.
- **Shared root / affected pages:** `ErpFiscalWorkspace` document area at `/erp/fiscal#documents`; all fiscal models presented through `ErpFiscalDocumentForm`.
- **Minimal refactor:** add an explicit “Novo rascunho” action to the existing shell and host the existing form in a slideover/full editor appropriate to its length. Keep list/detail as the resting workspace. Do not redesign the fiscal model builder, remove required fields, or reuse office-capture forms.
- **Preserve / regression checks:** model-specific NF-e/NFC-e/CT-e/MDF-e sources, sale/return snapshots, document numbering reserved by server, original-document filtering, idempotency key and pending recovery, configuration/establishment context resets, local drafts, validation errors, production gates, transmit/consult/contingency/events, and private artifacts. Closing/reopening must not accidentally replace a pending operation identity or discard a recoverable draft.

## L5 — P3: Headers, active tabs, and body introductions repeatedly restate the same location

- **Current evidence:** `frontend/app/components/erp/ErpCatalogPageShell.vue:13` renders the module navbar; line 34 adds a default description paragraph before every workspace. Finance then renders the current tab again as a large heading at `frontend/app/components/erp/ErpFinanceWorkspace.vue:339` immediately below its active navigation at line 329; Cash repeats the pattern at `frontend/app/components/erp/ErpCashWorkspace.vue:229` and line 240. Sales repeats its active button-tab label as an `h1` at `frontend/app/components/erp/ErpSalesWorkspace.vue:608`. On the office side, `frontend/app/pages/fiscal.vue:13` sets the navbar to the active child's label, and `frontend/app/pages/fiscal/clientes.vue:468` renders “Clientes” again above its filters.
- **Template comparison:** `.dashboard/app/pages/customers.vue:212` identifies the page once in the navbar and moves directly into filters at line 224. `.dashboard/app/pages/settings.vue:32` supplies the parent section heading; its nested Profile heading at `.dashboard/app/pages/settings/index.vue:57` adds a distinct task, rather than repeating the active menu label. Contextually distinct headings remain useful.
- **Expected pattern / UX impact:** the same module/tab identity currently consumes navbar, navigation, and body heading space, plus a permanent explanation. This lowers the number of records visible before scrolling, especially when filters already wrap. This is presentation debt, not a reason to delete safety or transactional explanation.
- **Shared root / affected pages:** `ErpCatalogPageShell` and the Finance/Cash/Sales workspace headers; Fiscal office shell/children. Catalog pages already support `showHeading` and should retain genuine subsection headings for multi-resource pages.
- **Minimal refactor:** make the body introduction optional/informational on demand, retain one page identity plus active navigation, and attach counts/refresh to a compact list toolbar or footer. For office Fiscal, remove only the duplicate child heading or centralize child actions into the shell. Keep distinct section titles, meaningful empty states, mutation confirmations, production warnings, and stale/error notices.
- **Preserve / regression checks:** accessible names for distinct sections and controls, counts sourced from server metadata rather than placeholders, refresh/loading behavior, permission-specific actions, mobile control fit, and information needed before irreversible operations. Do not apply a blind “remove all descriptions/headings” rule.

## L6 — P3: Sales uses a separate navigation and list grammar from the existing operational modules

- **Current evidence:** `frontend/app/components/erp/ErpSalesWorkspace.vue:566` implements four route-hash areas as a custom horizontal row of `UButton` with solid/outline states rather than `UNavigationMenu`. Its record list at lines 627–642 implements unlabeled desktop grid columns in clickable rows, and lines 644–661 provide custom previous/next pagination. Finance uses native highlighted `UNavigationMenu` at `frontend/app/components/erp/ErpFinanceWorkspace.vue:329`; Purchases does the same at `frontend/app/components/erp/ErpPurchaseWorkspace.vue:483`; Cash at `frontend/app/components/erp/ErpCashWorkspace.vue:229`. These are the same level of area navigation inside the same shared shell.
- **Template comparison:** `.dashboard/app/pages/settings.vue:38` uses `UNavigationMenu` for route navigation. `.dashboard/app/pages/customers.vue:290` presents repeated comparable records as an explicit table with named columns, and lines 313–325 use a counted footer plus `UPagination`.
- **Expected pattern / UX impact:** navigating Quotes → Orders → Sales should use the same visual grammar as moving between Finance/Cash/Purchases areas. The desktop rows make amount/status/establishment harder to interpret as repeated columns because there is no shared header. Custom pagination also changes the interaction model compared with nearby ERP lists. Mobile stacked records are a reasonable adaptation, and should not be removed merely to resemble the desktop template.
- **Shared root / affected pages:** Sales workspace, affecting quote/order/sale/return areas; reuse `ErpCatalogPageShell` and table/footer presentation rather than adding another shell.
- **Minimal refactor:** first replace only area buttons with the existing native navigation pattern, retaining current hashes and permission filtering. Then give the desktop list named columns using `UTable` and existing `erpOperationalTableUi` (`frontend/app/components/erp/erpPresentation.ts:6`), while retaining a compact mobile record list and the current detail overlay. Reuse an established counted pagination/footer, leaving existing data-loading and operations logic intact. This does not require new sorting/filter features.
- **Preserve / regression checks:** all four hashes/deep links, visible-area permissions, creation fallback when current area cannot create, detail permissions, stale list behavior, metadata counts, page boundaries, draft revisions/conflicts, quote/order conversion, returns, immediate-payment permissions, mutation idempotency/reconciliation, in-flight context switching, and modal state/focus behavior.

## Strengths worth preserving

1. **Dashboard foundation is intact.** `frontend/app/layouts/erp.vue:44` retains `UDashboardGroup`, native sidebar/search/navigation, workspace context in the header and user menu in the footer; this matches `.dashboard/app/layouts/default.vue:118–158`. `ErpCatalogPageShell` provides one reusable native panel/navbar/toolbar frame. The response should be consolidation, not replacing the product shell.
2. **A usable settings pattern already exists.** `frontend/app/components/erp/ErpSettingsSectionForm.vue:111–186` follows the template's naked horizontal task header, save action, subtle card, separators, and responsive label/control rows. It adds genuine API errors, pending/permission states, authority safety, and metadata-driven options. Group its content instead of rewriting its lifecycle.
3. **Shared visual tokens and on-demand editors already reduce drift.** `frontend/app/components/data-table/panel.ts:13–40` reproduces the template customer table/footer styles in reusable tokens; `frontend/app/components/erp/erpPresentation.ts:6` adapts them for operational content. `frontend/app/components/erp/catalogs/ErpCatalogResource.vue:389` uses that table surface and line 428 uses a slideover with explicit busy, context, and focus handling. Office pages also share distinct scroll/table/record contracts in `frontend/app/utils/pageShell.ts:18–34`; those intentional differences should not be collapsed into a single universal layout.

## Recommended sequence

1. Confirm L1 with populated browser data; fix the child scroll contract if reproduced.
2. Establish the shared presentation rules: one task heading, module navigation, filter location, counted footer, on-demand editor.
3. Apply those rules to ERP settings groups and company administration, then Fiscal creation, then Sales.
4. Validate populated/empty/error/stale/pending/restricted states on desktop and mobile. Preserve fiscal and commercial gates and verify operational recovery separately from visual acceptance. No execution or external-system acceptance is claimed by this report.
