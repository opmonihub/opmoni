# Navigation consistency audit

Scope: isolated source snapshot, settings/catalog/module navigation, 2026-10-23. Read-only semantic review; no product edits, dependency installation, tests, detector, or browser operations. Browser observations belong to the coordinator. All source references below are relative to this snapshot. Findings describe current code, not the earlier ERP acceptance recorded in memory.

Authority: `.dashboard/app/pages/settings.vue:4-26,38-46` and `.dashboard/app/layouts/default.vue:32-62,134-140`. The canonical pattern uses direct route links in a single primary toolbar group, a persistent parent settings panel, and a sidebar disclosure of the same destinations. Domain-specific ERP destinations and authorization are legitimate additions. The manifest requests `@nuxt/ui ^4.11.3` (`frontend/package.json:18`). Official Nuxt UI MCP NavigationMenu usage/theme documentation was consulted: [NavigationMenu](https://ui.nuxt.com/docs/components/navigation-menu). In horizontal orientation, nested arrays are spaced groups; `children` create submenus; root theme includes `justify-between`.

## N1 — P2: Sidebar-shaped groups produce the wrong settings/catalog toolbar

- Evidence: `frontend/app/utils/erpWorkspaceNav.ts:138-165` returns one nested array per group, each containing a `type: 'trigger'` item with `children`. ERP settings passes this directly to a horizontal menu at `frontend/app/pages/erp/configuracoes.vue:9,23-25`; catalog index repeats it at `frontend/app/pages/erp/cadastros/index.vue:9,18-24`. Settings groups are Empresa, Operação, Sistema, Administração (`erpWorkspaceNav.ts:75-118`). The canonical settings toolbar instead places General/Members/Notifications/Security as direct `to` links inside one array (`.dashboard/app/pages/settings.vue:4-21,38-40`); current office settings retains this basic shape (`frontend/app/pages/settings.vue:5-21,33-35`).
- Current behavior and impact: horizontal group spacing distributes the four independent arrays across the toolbar. Every destination is also behind a disclosure instead of being a visible local route link. The group is highlighted, while the specific selected destination is visible only in the open menu/content. Adding `w-full`/`flex-wrap` changes layout, not this data model. This explains the concrete complaint without treating Nuxt UI itself as broken. It affects both company settings and the catalog hub.
- Minimal future refactor: keep the authorized destination registry, but provide a separate toolbar projection with direct `to` links in a single group, as the template does. Use the project's existing horizontal overflow approach (`ErpFinanceWorkspace.vue:329-334`) for the larger ERP destination count; decide whether to show all authorized destinations or a visible active-group subset before implementation. Retain group metadata where it helps sidebar/search. A `justify-start` CSS override alone only addresses spacing, leaving the extra interaction layer.
- Preserve: company-active/read-permission filters, direct-owner-only Members/Office, route names, active child calculation, native link/disclosure keyboard semantics. Do not flatten 15 settings destinations into several unbounded mobile rows without browser acceptance. Code proves grouping/submenus; exact mobile geometry remains unmeasured.

## N2 — P2: Catalog local navigation disappears after selecting a destination

- Evidence: the catalog toolbar exists only in `frontend/app/pages/erp/cadastros/index.vue:14-25`. Each destination is an independent page, e.g. `frontend/app/pages/erp/cadastros/produtos.vue:23-46` and `.../precos.vue:53-78`, which invoke `ErpCatalogPageShell` without a toolbar slot. That shell only renders a toolbar when supplied (`frontend/app/components/erp/ErpCatalogPageShell.vue:28-30`). There is no `pages/erp/cadastros.vue` persistent parent. By contrast, `.dashboard/app/pages/settings.vue:30-46` and `frontend/app/pages/erp/configuracoes.vue:13-30` keep navigation around their child pages.
- Current behavior and impact: selecting Produtos removes the local destination chooser. Switching to Marcas/Unidades then requires the global sidebar or reopening the catalog index; mobile users must reopen the drawer. The index toolbar also cannot provide selected-destination feedback, because the index and destination never render together. This adds a second, short-lived navigation surface without a durable benefit.
- Minimal future refactor: choose one durable owner for local catalog navigation: project it inside the common catalog page shell or create a persistent parent in the existing nested-page pattern. Avoid stacking a new parent panel around child-owned panels. Keep page-level create actions in the existing navbar action slot.
- Preserve: existing `/erp/cadastros/*` URLs, per-catalog read/write grants, create-menu focus handoff (`.../precos.vue:32-49`), sidebar drawer close/focus restoration, company context isolation, and independently rendered resource forms. This is an interaction inconsistency, not proof that every catalog needs a new tab bar.

## N3 — P2: Independent stock registries omit a valid destination from sidebar and search

- Evidence: stock's actual UI includes `lots / Camadas de custo` and checks `erp.stock.lots.index` (`frontend/app/components/erp/ErpStockWorkspace.vue:12-28,78-82`). Its sidebar contract has only balances/movements/adjustments/transfers (`frontend/app/utils/erpModulesNav.ts:182-210`), and the permission lookup also omits lots (`frontend/app/utils/erpWorkspaceNav.ts:195-198`). Sidebar children come exclusively from that contract (`.../erpWorkspaceNav.ts:235-245,266-267`) and search exclusively from sidebar destinations (`...:314-327`). Template settings demonstrates a sidebar/local-navigation destination correspondence (`.dashboard/app/layouts/default.vue:37-61` versus `.dashboard/app/pages/settings.vue:4-20`).
- Current behavior and impact: a user with stock access can select Camadas de custo in the local toolbar but cannot find it in global navigation/search. On `#lots`, no stock child can be active because the contract does not recognize the hash; a user granted only lots read can have the whole stock sidebar module omitted (`erpWorkspaceNav.ts:276-278`). This is missing representation of an existing feature, not a request to remove that feature.
- Minimal future refactor: define stock destination IDs/labels/read actions once and project the same list into sidebar, search, and toolbar. At minimum add the existing lots destination and matching permission to the shared contract.
- Preserve: `#lots` deep links/back-forward, `erp.stock.lots.index`, first permitted area fallback, `query` preservation, native links, SSR-safe initial hash handling, and the cost-layer functionality itself.

## N4 — P2: Finance/Cash toolbar options disagree with permission-filtered sidebar

- Evidence: sidebar filters every module tab by read action (`frontend/app/utils/erpWorkspaceNav.ts:186-191,235-239`). Finance toolbar maps all three static options with no read filter (`frontend/app/components/erp/ErpFinanceWorkspace.vue:11-14,29-33,89-93`), defaults to obligations, and canonicalizes that hash (`...:94-107`). Cash maps both options without filtering and defaults to registers (`frontend/app/components/erp/ErpCashWorkspace.vue:8-29`). Finance's loader correctly checks the selected read action (`frontend/app/composables/useErpFinanceWorkspace.ts:21-22,70-71,302`); stock already provides a local permission-aware example (`ErpStockWorkspace.vue:19-28,78-82`). Template sidebar and settings toolbar expose the same destination set (`.dashboard/app/layouts/default.vue:37-61`, `.dashboard/app/pages/settings.vue:4-20`).
- Current behavior and impact: a payments-only user sees only Pagamentos in the sidebar but still sees Contas/Obrigações in the toolbar. Opening the finance root selects unauthorized Obrigações, although another tab is usable. The equivalent cash case is sessions-only access opening Caixas. Guards remain in place; this finding concerns misleading choices and entry-state feedback, not an authorization bypass.
- Minimal future refactor: derive toolbar/sidebar options and the default from the same permission-aware destination projection; select a valid requested hash or first permitted destination. Keep explicit denial feedback for direct URLs whose permissions were revoked.
- Preserve: fine-grained grants and viewer write restrictions, backend enforcement, explicit read-only/denied states, query/hash URLs and browser history, pending-operation recovery and authority resets. Do not change finance/cash recovery composables merely to simplify rendering. Validate grants shrinking during an open session as well as initial load.

## N5 — P2: Office settings duplicates its destination registry and already diverges in labels/order

- Evidence: `frontend/app/utils/settingsNav.ts:11-14,41-56,65-78` defines a reusable destination list, toolbar projection, and sidebar projection, with a same-list/same-order contract. The sidebar consumes it but appends Members separately (`frontend/app/layouts/default.vue:49-52`). The toolbar ignores `settingsTabs` and manually rebuilds its list (`frontend/app/pages/settings.vue:5-21`). Consequently the toolbar begins General → Members → Notifications → Security, while the sidebar begins Geral → Notificações → Segurança → optional office destinations → Members. The canonical lists correspond in label/order (`.dashboard/app/pages/settings.vue:4-20`, `.dashboard/app/layouts/default.vue:37-61`).
- Current behavior and impact: the same route has different visible language/position across adjacent navigation surfaces; Members moves from second position to last. Future route/grant additions require updating independent sources despite an existing reusable helper. This makes the office example useful as a structural baseline, but not a complete current consistency standard.
- Minimal future refactor: include the existing Members destination in the shared settings registry at the agreed position, call the existing toolbar projection, and apply the same Portuguese labels to both projections. Keep the distinct Equipe route/alias behavior until separately reviewed.
- Preserve: exact index matching, active prefix matching, active-account-admin ERP integration gating, office certificate/WhatsApp administration gates, `/settings/members` compatibility, and mobile drawer closure. Do not copy the template's sample Documentation link into product settings.

## N6 — P2: Settings root redirects to an unavailable page instead of a permitted destination

- Evidence: `frontend/app/pages/erp/configuracoes/index.vue:1-3` always redirects to `/erp/configuracoes/empresa`. Navigation allows an establishments-only member into settings through `erp.establishments.index`, independently of company-settings read (`frontend/app/utils/erpWorkspaceNav.ts:81-82,121-136,270-272`). Company form reading requires `erp.company.settings.show` (`frontend/app/composables/useErpCompanySettings.ts:15-25`), and the form then displays an access-denied message (`frontend/app/components/erp/ErpSettingsSectionForm.vue:129-131`). The template settings root is a real available General destination with `exact: true` (`.dashboard/app/pages/settings.vue:4-8`), rather than an unconditional redirect to a filtered-out child.
- Current behavior and impact: direct entry at `/erp/configuracoes` can land an authenticated member on a denied form even when Estabelecimentos or Módulos is available. This is a recoverable dead-end via the toolbar/sidebar, not a security failure. It also creates a mismatch between the permission-filtered menu and the section's default route.
- Minimal future refactor: resolve the first permitted destination using the same settings registry and redirect there; when no destination exists, show the existing shell with a truthful empty/denied state. Keep an explicit unauthorized deep link denied rather than silently switching it to another page.
- Preserve: SSR-compatible `navigateTo(..., { replace: true })`, direct/delegated access distinction, direct-owner-only Members/Office, stable child URLs, and company changes during navigation.

## Boundaries and positive contracts

- No scores for contrast, touch-target size, actual clipping, screen-reader behavior, or hydration health: those require rendered/browser evidence, deliberately not produced here.
- Keep `UDashboardSidebar`, `UNavigationMenu`, `UDashboardNavbar`, and `UDashboardToolbar`; existing Nuxt UI primitives already support the required pattern. No dependency or custom navigation primitive is justified by this audit.
- ERP has useful existing safeguards: active-company filters (`erpWorkspaceNav.ts:121-136`), no SSR hash read until mounted for sidebar (`layouts/erp.vue:8,12,32-34`), company-keyed page ownership (`...:11,90`), mobile drawer close plus visible-trigger focus restoration including hash-only navigation (`composables/useErpSidebarNavigation.ts:7-27`). Any consolidation must retain them.
- Nested arrays are not inherently wrong: the template intentionally uses a second group for external Documentation. The problem is assigning every ERP local navigation category its own spaced group and submenu, plus maintaining multiple projections by hand.
- Prior acceptance memory was used only to avoid treating the prior implementation as unvalidated or resetting its behavior. Current findings are independently sourced from the snapshot; none claim that earlier browser/test results validate this snapshot.

## N7 — P1: Fiscal sidebar destinations change the hash without selecting their promised workspace

- Evidence: Fiscal sidebar destinations are `nfe/nfce/cte/mdfe/certificates/events/invalidations` (`frontend/app/utils/erpModulesNav.ts:264-271`); they become `/erp/fiscal#<id>` links and hash-derived active items (`frontend/app/utils/erpWorkspaceNav.ts:223-245,266-267`). Search reuses those same links (`...:314-327`). The actual route simply renders `ErpFiscalWorkspace` (`frontend/app/pages/erp/fiscal/index.vue:1-7`). That component initializes local `activeArea = 'documents'` and draft `selectedModel = '55'` (`frontend/app/components/erp/ErpFiscalWorkspace.vue:4-6`), defines areas `documents/configuration/certificates/events/invalidations` (`...:23-26`), and uses plain buttons that only assign local state (`...:299-310`). There is no `useRoute`, route-hash watcher, or router update in the component or its composable. Document rows render the unfiltered `workspace.documents` (`...:337-354`), and the loader requests `/erp/fiscal/documents?per_page=100` without a model parameter (`frontend/app/composables/useErpFiscalWorkspace.ts:447-455`). The model selector is separately bound to `selectedModel` (`ErpFiscalWorkspace.vue:370-383`). Canonical settings aligns visible navigation with routed content (`.dashboard/app/pages/settings.vue:4-21,38-46`); the existing Finance workspace demonstrates the project's hash-to-area synchronization (`ErpFinanceWorkspace.vue:89-107`).
- Current behavior and impact: on initial `/erp/fiscal#certificates` or `#events`, the sidebar can highlight that destination while the content remains Documentos. On `#cte`, neither the document list nor the draft model switches to CT-e: the initial builder remains NF-e (55). Navigating between sidebar hashes on an already-open Fiscal workspace leaves whichever local area/model was selected, because no code consumes the hash. Conversely clicking local Configuração/Certificados/Eventos never updates the sidebar destination or browser history. Thus global navigation/search and primary content can describe different fiscal tasks. This is a navigation/model-selection defect, not evidence of an external fiscal dispatch or a gate bypass.
- Missing destination: Configuração is a real supported local area with a configuration form (`ErpFiscalWorkspace.vue:437-453`) and independent read action `erp.fiscal.configuration.show` (`useErpFiscalWorkspace.ts:38-39,122-129`). It is absent from the sidebar contract and permission mapping (`erpModulesNav.ts:264-271`, `erpWorkspaceNav.ts:203-209`), so absent from search. With only configuration read, Fiscal can be supported by the composable yet omitted entirely from the sidebar because no contract child survives filtering (`erpWorkspaceNav.ts:235-239,276-278`).
- Minimal future refactor: define one permission-aware fiscal destination mapping, synchronize the existing hashes with local area plus model on mount and subsequent hash navigation, and emit the matching route on local navigation. Preserve `#nfe/#nfce/#cte/#mdfe` as explicit model destinations (or documented compatible aliases) rather than silently treating them as generic Documentos. Add Configuração with its actual grant. If model-labelled links remain, make the list/model context match their labels. Use the existing native `UNavigationMenu` toolbar pattern and `to` links so active state and history describe the visible content; do not replace the fiscal composable or builder implementation.
- Preserve: all existing `/erp/fiscal#*` deep links and back-forward behavior, SSR-safe initialization because fragments are absent from HTTP requests, selected establishment/company/authority isolation, granular direct/delegated grants and read-only support, native mobile drawer close/focus restoration, typed builders for models 55/65/57/58, model-specific contingency restrictions, certificate rotation/recovery, idempotency/pending-operation ownership, and provider/homologation/production release gates (`useErpFiscalWorkspace.ts:117-140`, `ErpFiscalWorkspace.vue:37-40`). Coordinator owns runtime confirmation; this follow-up adds only source evidence.
