## Revision-aware deployment and compatible recovery

1. Apply the additive migrations before deploying authentication code. Preserve APP_KEY, credentials, existing rows and development sessions; do not flush Redis or reverse data migrations.
2. Deploy revision capture and fresh persisted-revision checks to every application instance before exposing direct reset or recipient recovery. Drain/restart long-lived application processes so no revision-ignorant authentication instance remains. Workers must use the compatible code before access delivery is enabled.
3. Before enabling reset routes, verify legacy revision-0 compatibility, rejected old-revision sessions, login/reset races and store failure against the intended isolated acceptance runtime. Initial identity creation captures revision 0; password login captures the value under its User lock. Never reread a later revision to upgrade an earlier password proof.
4. After any credential reset, recover only with an application version that retains these revision checks and understands the additive schema. A pre-revision app is incompatible even if its schema queries still execute. Keep registration/invitation/delivery/operation history and issued invoices; never restore old passwords or discard revision counters.
5. If no tested compatible recovery build exists, disable the affected entry points and restore service forward with revision-aware code. This procedure does not authorize deployment, configuration changes or development-session cleanup.
