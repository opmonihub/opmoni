## Context

See [proposal.md](proposal.md) for motivation and capability scope. The evidence baseline is [the audit](../../../docs/reviews/2026-10-23-template-consistency-audit/report.md), [visual plan](../../../docs/reviews/2026-10-23-template-consistency-audit/visual-alignment-plan.md) and [forms/setup plan](../../../docs/reviews/2026-10-23-template-consistency-audit/forms-and-defaults-plan.md). Its findings distinguish source-confirmed behavior, reproduced browser states and the unconfirmed populated-scroll risk.

The adopted [MarketUP functional research](../../../docs/reviews/2026-10-23-marketup-operation-nature/report.md) contributes multiple CFOP choices per nature, explicit defaults, product exceptions and separate configuration/execution transitions. Its authenticated client state and public guides do not establish server implementation, legal applicability or concurrency guarantees. Opmoni's native Laravel backend and existing template remain the base; no MarketUP visual language, tenant data or client stack is adopted.

Nuxt UI `^4.11.3`, `.dashboard` and existing Opmoni shells already supply the required primitives. The base green/zinc palette and Public Sans match; ERP's light-mode semantic overrides, independent navigation projections and accumulated form framing cause divergence. Native product validation already permits absent fiscal fields. Legacy product creation prefills Business defaults, but neither legacy prefill nor current standalone tax rates implement linked multi-tax profiles.

Laravel owns Company authorization, catalog writes, financial effects, snapshotting and fiscal issuance inside the existing runtime. `ErpCommercialDraftService` freezes product/reference facts and `ErpFiscalIssuanceService` compares posted source classifications. `ErpCompanyProvisioning` currently creates access/establishment/subscription only. Native invoice scheme/layout models exist without verified active default/rendering consumers. `services/fiscal/` remains absent and this design does not create it.

## Goals / Non-Goals

**Goals:** Reuse current shells, components, access fencing and operation identities; provide short basic tasks; make native defaults actually usable; resolve explicit product tax inheritance and operation-nature CFOP rules coherently before snapshots freeze; preserve compatibility and history through additive changes.

**Non-Goals:** A second design system, generic configuration/rules framework, new dependency, full legacy or MarketUP import, automatic legal classification or unreviewed fiscal-nature presets, tax-engine replacement, wholesale address/provider migration, fiscal service extraction, historical snapshot repair or any production rollout. NCM/CEST remain explicit product facts; CFOP remains operational. Detailed tax rates, CFOP reference versions and legal applicability require authoritative verification before new lookup data is introduced. Automatic purchase CFOP resolution, variant-specific exception rules and new fiscal operation kinds are outside this addition; existing purchase and return contracts remain compatibility constraints.

## Decisions

### 1. Align semantic roles and page families through existing shared sources

Use `.dashboard/app/{app.config.ts,assets/css/main.css,layouts/default.vue,pages/settings.vue,pages/settings/index.vue,pages/customers.vue}` as reference, with `pageShell.ts`, `data-table/panel.ts`, `data-table/sheet.ts` and `erpPresentation.ts` as product-local adapters. Measure resolved light/dark tokens, actual loaded font, controls, borders, sidebar/navbar and outer gutters under matched conditions before changes. Keep native root scale and md ordinary controls; retain purposeful small row actions and wide operational columns.

Reconcile `main.css`'s `[data-erp-workspace]` light override through native role variants and shared semantic roles with measured contrast. Equivalent roles must converge across office/ERP; do not simply delete a prior contrast correction or patch generated themes. Ordinary settings start from the reference `lg:max-w-2xl` composition; long editors use justified wider surfaces. Document any exception with its actual task rather than set one universal width. Test teleported overlays and office → ERP → office navigation.

Alternative considered: global CSS scaling or another ERP palette. Rejected because they would preserve role/hierarchy drift and introduce a second visual system. The archived UI design remains immutable; new evidence explains revised decisions.

### 2. Keep one destination source with explicit projections and controlled expansion

Extend `erpWorkspaceNav.ts` and the existing registry instead of inventing another navigation tree. Store destination identity, route/hash, required grants and optional fiscal area/model in one contract. Derive sidebar, search, direct local toolbar links, first-permitted root and workspace selection from it. Include existing stock `#lots` and Fiscal configuration/certificates/events; model destinations synchronize list/create context. Preserve canonical URLs, SSR-safe hash hydration and explicit denial for unauthorized deep links.

For settings/catalogs, use one flat array of permitted direct links in the native horizontally scrollable toolbar, keeping the active link reachable. Preserve the toolbar around child pages through one shell/panel owner; refactor child composition before adding a parent so panels are not nested. Finance/Cash/Sales use the same destination projection rather than independent static tabs or action buttons. Sales lists reuse existing table/footer tokens while keeping useful mobile rows and server metadata.

Use the office `foldedSidebarChildren` behavior and a controlled single expansion value shared by both ERP menus. Reset manual folding only when the owning module/context changes. Another group's expansion can coexist with the pinned active child, not a second fully disclosed sibling list. Use the installed empty controlled value and `type="single"` API; changing the prop alone is insufficient. Preserve disclosure keyboard behavior, collapsed popovers and `useErpSidebarNavigation` close/focus contracts.

Alternative considered: CSS alignment fixes and independent accordion state per menu. Rejected because they leave false destinations and allow two fully expanded groups. Reuse/extend the office helper only when both surfaces' behavior remains covered.

### 3. Use progressive form sections without changing permissive basic contracts

Keep `ErpProductCatalogForm` in the established catalog editor with identity/unit/kind and optional SKU/price visible initially. Keep native service/stock rules. Advanced Commercial details, Fiscal and Variants disclose on demand using installed Nuxt UI components. A resolved native unit can initialize the selection; lookup failure cannot fabricate a selection. Reopening/closing a section never resets saved values, variants, null price inheritance or archive state.

Keep one form state/identity and place Save/Cancel in the reachable catalog drawer footer, associating the primary control with the actual form ID. Maintain pending/disabled states, server field errors, first-error focus and return focus. Use existing dirty-close behavior; where absent, add one explicit discard confirmation shared by close/backdrop/Escape rather than silently lose entered edits. Do not add a transparency patch: the settled inspected overlay was opaque.

Extend typed `ErpSettingsField` metadata with groups and explicit code/decimal/reference semantics. Preserve rates as canonical decimal strings; code selectors use string values with human descriptions and verified enumerations. Current numeric CST values are visible review cases, not automatically padded. Company identification/address/preferences/fiscal tasks get meaningful groups without changing hidden values or splitting one save into accidental partial effects. Administration adopts native controls and deliberate editors; detailed permissions move behind a disclosure without changing their meaning or owner restrictions.

For contacts, define a reusable address projection that reconciles `state`/`uf`, municipality text and municipality code. Preserve unrelated extension keys. A municipality change must select a verified coherent code or explicitly invalidate readiness; do not silently retain the old code or require all fiscal facts for basic contact save. Currency/city legacy namespaces remain compatibility dependencies.

Fiscal field descriptors carry actual payload/error path, label, type and required condition. Align backend structured errors and frontend mapping for nested CT-e/MDF-e facts, and keep strict builders. Finance selections use one compatibility predicate for options and submit eligibility; incompatible retained values stay visible for correction instead of being silently submitted or cleared after a failed fetch.

Alternative considered: reproduce all legacy required fields or merely hide sections with CSS. Rejected because current optionality and preservation contracts are intentional, while unresolved defaults and incorrect errors require behavioral work.

### 4. Reuse bounded catalog lookup and selected-record hydration

Adapt `ErpCatalogReferenceSelect` where compatible; add a focused product/variant adapter for the commercial shape. Query matching company records with server pagination/search, show product name plus SKU/variant, and separately hydrate the current selection by an authorized ID. Preserve unavailable historical choices visibly; new use still requires active compatible records. Reuse the pattern in purchase references where whole-collection loading exists. Cancel/discard late results on company/authority changes. Do not fetch every page before editing and do not replace selections with the first result after failure.

### 5. Add one native setup service and explicit default identities

Introduce a focused company initializer called inside the existing provisioning transaction. A code-owned manifest defines `br-basic-v1` settings, stable native keys and the actual consumer for each item. It does not contain secrets, user fixtures or tax rates. Keep owner/Matriz/pending-subscription behavior intact. Persist ordinary operating preferences using the existing settings service; add a company-scoped setup-state record for preset version, revision and native default references rather than repurpose opaque legacy IDs.

Proposed additive `erp_company_setup_states`: unique `erp_company_id`, preset version, revision, ISO currency, nullable native default unit/customer/invoice-scheme/layout references and preset-owned record keys. Every reference is validated and constrained to the same company using the project's supported composite-key pattern. This creates an explicit namespace separate from `default_unit`, `currency_id`, `purchase_currency_id` and `cidade_id`; the settings payload exposes it as `native_defaults` with typed IDs/labels. Unresolved legacy fields remain preserved and documented.

Initial choices: timezone America/Sao_Paulo, date `d/m/Y`, time format 24, January start, native BRL, existing FIFO/overselling-off preferences; UN uses whole units without conversion. “Consumidor final” is an ordinary company customer referenced by the native default pointer, without invented document/address/municipality. Product creation consumes the native unit; counter sale consumes the permitted native customer. A user-defined record with the same name is not automatically preset-owned. A customized or inactive UN is a visible reuse/conflict decision, not an overwrite.

Native `ErpInvoiceScheme`/`ErpInvoiceLayout` are used, not duplicated. Connect the chosen scheme to `ErpCommercialNumbers` and sale creation: the existing company/establishment/document sequence remains authoritative, honors start only when uninitialized, skips collisions and never resets when a scheme changes. New companies get the requested blank-prefix/four-digit sale presentation; quotes/orders retain their existing scheme. Existing companies without an explicit adopted scheme retain current S-/six-digit behavior, even when reconciliation supplies a compatible native scheme. Existing draft numbers are immutable. Do not use `invoice_count` as a competing allocator.

Connect the localized commercial layout to an authenticated company sale representation/print action and freeze its relevant labels/settings with the commercial document. Add only the focused representation needed for this default consumer; do not present it as a fiscal auxiliary artifact or reuse DANFE rendering. The existing payment receipt remains a payment receipt.

Alternative considered: a database seeder copying BusinessUtil and legacy IDs. Rejected because native ownership/default relationships and consumers differ, and seed-only rows would not make a usable workflow. Retain only settings with verified consumers; do not automatically adopt legacy 25% margin, tax-inclusive pricing, unused shortcuts or hidden switches.

### 6. Reconciliation uses explicit previews, company locking and missing-value semantics

Direct owners can POST preview/apply under `/api/v1/erp/company/initialization/{preview,apply}`. Guard both with current direct ownership and standard Company/session assertions. Preview returns sanitized item statuses (`create`, `reuse`, `skip`, `conflict`), before/after effective choices and a server-bound fingerprint/version. It binds actor, selected company and relevant setup/preferences/catalog revisions; apply rechecks those facts under company/setup locks. A changed relevant precondition returns recoverable 409 and requires fresh preview. Replaying the same applied operation uses the existing operation identity/reconciliation convention.

Missing means absent, never a truthiness test. JSON merges operate on manifest-owned paths, preserving explicit null/false/zero/empty values and unrelated nested settings. Baseline records use stable keys plus native uniqueness and the setup-state manifest mapping, never display-name matching alone. One lock order starts with authority/company, then setup state and referenced records. Initialization and reconciliation converge under concurrent calls without duplicate defaults. Required failure rolls back the transaction; safe unresolved compatibility issues are returned as conflicts and are not represented as completed setup.

The first reconciliation UI belongs to company settings, with a concise preview and explicit apply action. Delegated office membership, manager status or Super Admin alone do not grant this cross-catalog setup action. New-company provisioning remains internal to its already authorized creation flow; public registration gates remain unchanged.

### 7. Model tax profiles as revisioned native records with explicit product intent

Use new company-owned profile and immutable revision tables. A profile stores name/status/current revision; each revision stores supported string codes, exact rates and limited applicability metadata. Initial applicability is explicit supported regime, product goods/service context and operation movement where supplied. This filters an explicitly chosen profile; it does not automatically select a rule by arbitrary destination conditions. Do not add an establishment-specific default in this first version; preserve room for an explicit later contract.

Profile fields do not store an operational CFOP default or exception. The nature resolver below consumes the actual operation context independently; its revision/provenance joins the reviewed operation without changing profile inheritance precedence or adding another commercial tax amount.

Products retain current fiscal columns as explicit-value storage, with an additive nullable profile relationship and per-field intent metadata. Modes are `value`, `inherit` and `unset`; company-default selection is explicit. No metadata means the current contract: non-null fields are explicit values and existing nulls are unset. Omitted PATCH keys remain unchanged; an explicit null remains clear/unset. Adoption writes inheritance modes deliberately after showing effective changes. Conflicting intent/value combinations return 422 rather than guess. Changing a profile does not bulk-update products.

An explicit product value resolves directly; explicit unset stops fallback and zero remains a value. An inherited field resolves from the selected applicable profile's field, then an explicitly configured compatible company field/default profile, else remains unresolved. A selected profile that is archived, missing, unavailable or incompatible is a resolution error, not a substitute-default trigger. Profile-field absence and explicit unresolved state remain distinct. Existing stored combined CST/CSOSN defaults are consumed only after regime/type validation; ambiguous numeric values require review. A virtual GET fallback is not confirmed fiscal setup.

For new-product creation, an explicitly configured company default profile is offered as visible “Padrão da empresa” inheritance with an effective preview and a “Sem configuração tributária” option. No hidden tax values are fabricated. Existing-product editing preserves its prior intent until explicit adoption. An invalid default must remain visible for correction or an explicit basic-save choice, rather than silently select another profile.

Use `/api/v1/erp/tax-settings/product-tax-profiles` for paginated CRUD/archive, a typed company default-profile setting and an authorized resolution preview. Extend the current granular permission registry with `erp.product-tax-profiles.index/store/update/destroy`; archive retains revisions. Product assignment continues to require product write authority; setting a company default requires settings-write authority. New delegation grants are explicit allowlist entries and do not broaden existing delegated access. Internal operation resolution reads only authorized same-company configuration; it does not grant profile administration.

Alternative considered: copy every profile field onto each product or introduce an arbitrary rules language. Rejected because copying defeats reusable updates and scripting introduces unspecified precedence/calculation risk. Revisioned records plus a small deterministic resolver fit the existing catalog architecture.

### 8. Extend the native operation nature with scoped CFOP rules

Retain `ErpOperationNature` and `/api/v1/erp/tax-settings/operation-natures`. Its existing `cfop` remains the single explicit default and the compatible old payload field; do not introduce a competing default flag. A legacy row exposes an implicit one-choice allowed set without bulk-inserting or reclassifying records. Additional active choices extend that set. Reject removal/archive of a default without a valid replacement in the same transaction. Preserve existing IDs, establishment scope, status, description and unrelated `fiscal_metadata` keys.

Add a monotonic `configuration_revision` to the nature and focused same-company child tables for allowed choices and product exceptions. An allowed choice binds nature, canonical CFOP and verified reference version, with uniqueness per nature/code. An active exception binds that nature and one native product to one of its active allowed choices; its effective uniqueness is per nature/product and it covers that product's variants. Use the existing composite ownership constraint pattern for nature, choice and product references. Establishment applicability is inherited from the nature; do not add an independent exception scope or a second operation-nature catalog.

Use a code-owned, versioned, read-only CFOP reference dataset whose origin and supported metadata are verified against authoritative sources in the implementation baseline. Canonical new codes are four-digit strings; descriptions and actual supported applicability metadata accompany lookup. Do not derive legal treatment from MarketUP property names or prefix alone. An unverified legacy string stays readable and unrelated edits remain possible, while new fiscal preparation exposes it as unresolved until deliberately confirmed or corrected. No blanket code normalization, reference adoption or active fiscal-nature seeding occurs during migration or initialization.

Expose bounded reference lookup at `/api/v1/erp/tax-settings/cfops`, and bounded choices/product-exceptions under the existing nature resource. Reuse native catalog authorization, attribution and error envelopes. Nature index authority permits its lookup; existing nature write authority governs configuration, while a product-write grant alone does not. Source-write authority permits an explicit line choice only from the authorized nature's allowed set; it does not grant rule administration. Foreign direct resources remain 404 and foreign/incompatible relationships 422.

All root/default, child, exception and archive writers lock the nature, validate current authority and advance its revision atomically. New collection/exception writes require `expected_revision` and return recoverable 409 on stale review. Existing single-CFOP clients retain their payload shape; their writes also lock and advance the same revision. Keep historical child identities rather than cascade-delete used rules. Default changes may leave a redundant but valid exception; do not silently rewrite it or other product rules.

Use a focused CFOP resolver alongside the product-tax resolver. Its order is an authorized explicit line choice, an active applicable nature/product exception, then the nature default, otherwise unresolved. Invalid explicit choices and encountered active exceptions with invalid targets return field errors without falling through. A valid higher-priority choice does not evaluate a lower-priority exception as its replacement. Validate the actual company, permitted establishment, movement, known origin/destination and selected supported model; missing required context remains unresolved. Presence of a profile does not select a nature or declare fiscal intent. Existing sale nature selection remains the source; fiscal configuration cannot silently replace a reviewed choice.

Optional new `lines.*.cfop` input represents an explicit line choice, not a product attribute. On creation, omitted/null means no explicit choice. On existing-line updates, omission preserves the current choice/facts and explicit null deliberately clears the override for reviewed re-resolution. A changed product, nature, explicit choice or relevant context requires a fresh reviewable calculation before posting. No unrelated edit opts an old draft into product-exception resolution.

Return a versioned `cfop_resolution` containing effective code, source (`explicit`, `product_exception` or `nature_default`), nature identity/revision, relevant choice/exception identity, reference version and relevant context fingerprint. For new snapshot versions, the existing `operation_nature.cfop` remains usable by readers as the effective line code; add an explicit `default_cfop` and separate provenance so an exception is not confused with today's catalog default. Old snapshot shapes keep their existing meaning and validation without fabricated metadata or current-rule fallback.

Reuse existing catalog editors, native reference selectors and operation review surfaces to expose these functions. This is a functional addition to the current template. Saving configuration has no stock, finance, issuance or external-provider effect. No `IsSystem`/`IsStockMovement` flags or tenant-specific MarketUP mappings are imported; reviewed baseline nature presets remain deferred.

Alternative considered: duplicate one nature for every CFOP, assign a universal CFOP to each product, or put relational rule sets in arbitrary profile metadata. Rejected because those approaches duplicate native identity, lose operation context and weaken scope/uniqueness validation. A scalar compatible default plus focused children and one aggregate revision keeps the extension bounded.

### 9. Resolve once at operational boundaries and preserve reviewed snapshots

The server product-tax resolver returns effective values, field sources, unresolved/applicability errors and profile/default revision; the focused CFOP resolver supplies the operational result from decision 8. Product previews use only the context they actually have. Operational preparation captures both outputs and their separately identified revisions coherently within the operation transaction. Use the authority/company-first lock order, followed by setup/default references, stable profile and nature identities and then source effects; all affected writers must participate in this order. Check reviewed fingerprints before effects and return 409 on stale relevant revisions. Immutable profile revisions, locked nature rules and versioned snapshots prevent mixed-field reads. Lookup/unavailable-reference failures preserve the draft and never fabricate a successful resolution.

On a new eligible draft, resolve once and return reviewed tax/CFOP facts. An ordinary edit preserves unchanged-line facts even if a profile, default or product exception changed; changing product/context or explicitly refreshing returns a fresh reviewable calculation. Save refresh and post remain separate actions; posting cannot silently recalculate with newer rules. Added/replaced lines resolve under a coherent revision set recorded per line and operation. Keep old incomplete drafts reviewable without automatic adoption. A non-fiscal basic operation may remain unresolved under its existing contract; explicitly invalid supplied references are still rejected. Standalone `ErpTaxRate` and operation-nature facts keep their current totals/CFOP role; the profile is not an additional generic tax amount and cannot double-charge.

Add explicit nullable `fiscal_model`/intent to eligible sale drafts (`55` or `65`; null means no declared fiscal intent). Existing drafts/sales default to null without retroactive reclassification. Profile presence never sets intent. Resolve the selected model's source-readiness rules before a fiscal-intended sale is posted, rechecking source facts/authority under the posting transaction. Retain incomplete drafts with real field paths and actions to correct or refresh. CT-e/MDF-e keep their separate typed source models and do not acquire a goods-profile requirement.

Posting freezes effective tax/CFOP facts and provenance together with the existing immutable sale/stock/finance effects. Linked NF-e/NFC-e preparation consumes those frozen facts and preserves `ErpFiscalIssuanceService` equality checks; it does not rerun exception precedence or overwrite the frozen nature from current issuer defaults. Current issuer/configuration compatibility is still checked and a mismatch fails before dispatch. Old single-CFOP snapshot readers, purchase-line references and return-specific source checks remain supported without adding automatic purchase resolution or changing supported return codes. Historical incomplete sources show their existing limitation and supported correction path; today's catalog/profile cannot repair them. Model validation, certificate revisions, signing/transmission identities and production gates remain unchanged.

Alternative considered: resolve defaults for the first time at issuance or silently on every post. Rejected because either can change reviewed facts or make frozen Sales classifications inconsistent with fiscal preparation.

### 10. Preserve current security, recovery and fiscal boundaries

All APIs retain relative `/api/v1` through private Nuxt ingress, session-selected Company plus `X-Company-Id`, delegated Account assertions, CSRF, non-cacheable protected responses and existing error envelopes. Do not accept payload IDs as context selectors. Foreign direct resources return 404, foreign related references 422, revoked access 403 and stale company/revision conflicts 409. Metadata and setup previews omit credentials and private paths. No migration reads or changes certificate secrets.

New long-lived UI work binds responses and operation keys to the captured Company/Account/session/authority and discards stale results. Existing pending-operation fingerprints and recovery ownership remain in the workspace composables; visual/editor extraction must not replace them with component-local fake success. Fiscal actions continue through Laravel's existing typed builders/queues and current private storage; no external provider is called by setup, preview or tax readiness.

### 11. Deliver reviewable dependent phases and targeted evidence

Implement visual/navigation contracts first, then typed code fixes/basic forms, native setup, profile and nature/CFOP data/resolution, commercial/fiscal snapshot integration and remaining form corrections. Verify canonical CFOP reference provenance and supported context checks before exposing new choices. Shared layouts/tokens/API types and final builds are sequential. Parallel work, if explicitly selected during apply, requires disjoint file ownership and isolated project-root worktrees. Reuse a suitable worktree and preserve dirty/untracked user work.

Use behavior tests for authority, navigation, field intent, snapshot revisions, setup idempotency and recovery. Verify geometry/colors through matched browser evidence, not source-string assertions. Desktop 1366px, mobile 390px, one intermediate viewport, light/dark and 200% zoom cover representative active modules and office regressions; use the same root scale/theme/sidebar/content state for comparisons. Reproduce the populated office-Fiscal scrolling risk before proposing a change. Browser mutations use an isolated test runtime whose source mounts and stores are verified.

## Risks / Trade-offs

- **Broad scope touches shared components** → phase delivery through real consumers and validate office/admin regressions; avoid changing unused hubs to claim progress.
- **Exact template tokens reduce prior contrast** → record real foreground/background states and resolve equivalent shared roles before removing ERP overrides.
- **Stored legacy numbers resemble native IDs/codes** → keep explicit namespaces, preserve unresolved values and require verified mappings/review.
- **Seeded defaults have no consumer** → completion requires an actual product/counter-sale/numbering/commercial-rendering flow; model existence alone is insufficient.
- **Profile/default changes race review or posting** → immutable revisions, coherent default state, optimistic reviewed fingerprints and independent process tests.
- **Nature choices/exceptions race configuration or posting** → one aggregate revision, same-company uniqueness, authority/company-first stable lock order and independent writer/posting tests; a legacy writer must not bypass revision changes.
- **A CFOP reference is mistaken for legal approval** → verify reference provenance and supported context explicitly, keep unknown legacy facts unresolved and do not seed tax mappings from the inspected tenant.
- **Snapshot expansion breaks old documents** → versioned additive provenance and old-shape readers; no historical backfill or current-default fallback.
- **Users perceive profile completeness as fiscal authorization** → separate basic save, applicable model readiness, local generation and actual provider outcome in labels and tests.
- **Whole-unit UN is unsuitable for an existing company** → apply only to fresh baseline; preview conflicts and preserve existing decimal/conversion choices.
- **Changing numbering presentation creates collisions** → retain existing scope/sequence, skip used numbers, preserve existing-company behavior and immutable draft numbers.

## Migration Plan

1. Verify the selected isolated worktree and runtime, and record current tracked/untracked work plus baseline canonical/audit evidence. Do not reopen the archived UI change.
2. Add tables/columns/indexes for setup state, profile/revisions, product intent, nature configuration revision, CFOP choices/product exceptions and fiscal-intent/snapshot metadata. Use additive migrations through `php artisan migrate --force --no-interaction`. Check existing default/uniqueness conflicts before constraints; report conflicts without destructive cleanup. Existing nature codes remain implicit compatible defaults rather than being mass-normalized or assigned imported exceptions. No `migrate:fresh`, identity recreation, key rotation or environment changes.
3. Deploy backend readers/writers accepting existing single-CFOP payloads and old snapshot versions before enabling new configuration/resolution consumers. Every legacy/new nature writer participates in revision advancement before coherent readers are enabled. New capabilities remain unclaimed until end-to-end local contracts pass. New-company provisioning uses the initializer; existing companies require preview/apply. Do not run automatic blanket reconciliation, fiscal-nature seeding, product adoption or historical re-resolution during deployment.
4. Run focused frontend/backend checks, formatting, isolated independent PostgreSQL/Redis races and the appropriate full check matrix from README. Record browser evidence and explicit live-provider limits in a new implementation evidence artifact; prior audit acceptance is not fresh implementation proof.
5. On regression, restore a compatible application checkpoint while retaining additive tables/data and ensuring its readers understand any newly posted effective-CFOP snapshot shape. Do not drop profile/rule history, reset sequences, replay operations or repair posted snapshots as rollback. Update reconciliation/delivered-versus-pending documentation only after actual validation; sync/archive and production release remain separate actions.
